# Include code output in a page or quiz

A code block in a page or quiz can pull in a script's own source and
what it produces when run, instead of you pasting either in by hand --
keeping the coursework and the code it's demonstrating in sync. Python
(`tent_pole.doit_rules.python`) and R (`tent_pole.doit_rules.r`) both
work this way -- a third language would get its own doit rules module
alongside them, generating the same kind of `.out`/`.stout`/`.crash`
artifact.

## Basic usage

````markdown
```python {include=demo.py output=true}
```
````

renders the syntax-highlighted contents of `demo.py`, a "Taken from:
demo.py" download link, and the script's captured stdout. With
`tent-pole build` from [start a new project](new-project.md), `demo.out`
is generated by actually running `demo.py` -- nothing to write by hand
beyond the code block attribute itself.

Included files in subdirectories are uploaded under the matching
subdirectory of Canvas's managed `tent-pole` folder. This preserves
distinct files with the same basename, such as lecture variants both
named `HelloWorld.java`, without renaming the downloadable source.

An R script works the same way, with `chunk=` to pull in one named
section of a longer file rather than the whole thing:

````markdown
```r {include=demo.R chunk=summary-stats output=true}
```
````

-- see [install](install.md#for-r-support) for the one extra
dependency (`evaluate`) this needs.

`chunk=` works for Python too, including a marker nested inside a
`def`/`class` body -- the displayed source is dedented so it reads as
standalone code:

````markdown
```python {include=demo.py chunk=average-body}
```
````

-- but only for display: Python's `output=`/`stout=`/`crash=` aren't
chunk-aware the way R's are (see the `chunk=` attribute below).

## Attributes

- `include=<file>` -- the source file to render. Required for anything
  below to do something.
- `output=true` -- run `<file>` as a plain script; show its captured
  stdout under an "Outputs:" label.
- `stout=true` -- run `<file>` as if typed at an interactive REPL
  instead; show the transcript (`>>> `/`> ` prompts included) under a
  "Prints:" label. Different from `output=`: it's a REPL session, not
  a script's stdout.
- `crash=true` -- `<file>` is *expected* to crash; builds its
  traceback as a `.crash` artifact and renders it under a "Crashes:"
  label, instead of failing the build the way an unexpected crash
  would.
- `compile-fail=true` -- Java only: the source is *expected* to fail
  compilation, so the compiler diagnostic is captured as a `.crash`
  artifact and rendered under the same "Crashes:" section without
  treating the failure as a broken build.
- `hide_crash=true` -- builds the same `.crash` artifact as `crash=`
  or `compile-fail=`, but doesn't render the "Crashes:" section. For
  a question or page that asks "will this code crash?" without
  answering itself in the same breath.
- `chunk=<name>` -- Shows only the named chunk's own source rather
  than the whole file -- `#+ chunk-name` marks where a chunk starts
  (knitr's own `spin()` convention, nothing tent-pole-invented), `#'`
  marks prose, and a chunk runs until the next marker or end of file.
  A marker can sit at any indentation -- nested inside a Python
  `def`/`class` body, say -- and the shown source is dedented, so it
  reads as standalone code rather than carrying its enclosing block's
  indentation along.
  - **For R**: `output=`/`stout=`/`crash=` still run the chunk's
    *full dependency chain* (every chunk up to and including the
    named one, in the same file) -- `chunk=` only changes what's
    *shown*, never what actually executed; chunks in the same file
    share state (variables, loaded packages) the same way lines later
    in one script always could, chunks in different files never do.
  - **For Python**: `chunk=` is display-only for now. Combining it
    with `output=`/`stout=`/`crash=` isn't supported -- those still
    only ever run the *whole* file, exactly as without `chunk=` at
    all. Chunk-aware execution needs its own design once there's a
    concrete use case for it (unlike R, a marker nested inside a
    function/class body doesn't correspond to anything that runs when
    the file runs top to bottom -- it only runs if and when something
    calls that function, so "the chunk's own output" isn't
    well-defined the way it is for a flat R script).
- `plot=true`/`plot=<n>` -- R only. Shows the chunk's first captured
  plot (or its `<n>`th) as an inline image, under a "Plot:" label. A
  chunk producing fewer plots than asked for is a build error, not
  something caught silently.

Any combination can appear on one code block (source is always shown;
`output=`/`stout=`/`crash=`/`compile-fail=`/`plot=` each add their
own section below it).

## Works the same in a quiz

The same attributes work in a `.quiz.md` question's code blocks -- see
[write a quiz](write-a-quiz.md) and
`dev/sample-course-python/question-types-quiz.quiz.md` for a worked example
(Questions 4-6 there specifically compare `include=` with and without
`output=`/`crash=`).

## Preview without Canvas

`code-include-filter` resolves the same attributes with no Canvas API
access at all, for `tent-pole build full`/`tent-pole build quiz_full`
-- see [write a page](write-a-page.md#standalone-preview-no-canvas-access).
